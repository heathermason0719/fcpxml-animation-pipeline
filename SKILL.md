# AfterForge

Work on the user's current creative goal. A project is a film series; an episode is one video; each episode can have independent production versions. Understand the episode, develop an expression, try it with real pictures and sound, revise, deliver, and retain useful experience. These activities repeat in any order. Do not narrate stage bookkeeping.

## Enter the work

Use the user's workspace and explicit episode/version selection. Inspect existing inputs before asking for files. Default writes stay in `AfterForge/`; `user-inbox/` is user-owned and read-only. Never alter original FCPXML, media, or an FCP library. Do not infer input selection from the newest folder name.

For a first-time user, explain how to create and name a submission folder under the workspace's `user-inbox/`, place the materials there, and provide that exact folder path. Script-first discussion needs the full script and the intended episode/topic; reference pictures, footage and style examples are optional. Rough-cut work needs the matching exported FCPXML/FCPXMLD and reference video, plus enough narration evidence (script, subtitles, or evidenced absence); suggest exporting both from the same timeline revision and keeping source media accessible. Inspect what is already supplied. If it is insufficient to understand the content, request only the missing essentials. If discussion is possible but production inputs are incomplete, explain the limitation and ask whether to supplement first or discuss first. Complete inputs let you proceed with understanding autonomously. Keep existing intake checks; later source binding uses the normal new-version path and never silently rebinds a version.

Read the concise `AfterForge/工程/创作记忆.md` first when it exists, then only relevant cases. Read this version's `frame.md` for concrete visual defaults. Series memory describes understanding and choices; it does not silently override an existing version's visual source. Retire old compromise-based aesthetic defaults from fresh work: retain useful narrative, legibility and font-compatibility experience, but derive this work's design from its content and confirmed concepts. One approval is not a permanent personal preference. When old series defaults contain withdrawn taste rules, choose `useSeriesDefaults: false` for fresh work and leave historical frames unchanged.

Visual specifications supply typography, color, layout and motion defaults only. Historical stage, approval or reopening instructions embedded in a copied specification have no authority over schema 3.0 work. Use this Skill and the work-model contract for operations and user decisions. When explicitly continuing a legacy project, check its root Agent instructions and series defaults before production; synchronize them only within the user's migration/cleanup authorization, leaving historical versions untouched.

Use `scripts/afterforge.py` for normal work-model operations. Read `references/work-model-contract.json` for vocabulary and `references/hyperframes-single-source.md` when authoring/rendering. No Stage Contract or stage resolver is needed for schema 3.0 work.

## Understand and design

Start from the whole argument: what should the audience understand differently, what does the original footage show, and what does narration establish? Model meaningful segments in `brief.segments`. A segment may have zero or many animation cues. Do not allocate animation sentence by sentence or impose a fixed percentage.

Propose concrete animation ideas after reading the full script and inspecting available rough-cut footage. Discuss additions, removals, changes and merges with the user; organize each idea's purpose, visual relationships, materials, text, motion and semantic anchors yourself. Keep `cues` as the single editable current plan. Before generating concepts, summarize the complete proposed production list, ask whether anything should be added, and wait for an explicit answer. Discuss additions and summarize again; a vague reply does not close the discussion. Save the presented snapshot and closing question with `update operation: "creative-planning", action: "present"`, then record the real reply with `action: "close"` and its `planId`. These are creative records, not production or approval gates. Do not invent assent or create a parallel plan document.

Resume from `status --summary`'s `creativePlanning`: distinguish current agreed content, waiting replies, content needing discussion and superseded history. Full status and `--cue-id` retain the relevant snapshots and call history. Later explicit local requests proceed directly; when recording a revised local plan, use the actual instruction as its source if it already resolves that scope. Substantive changes to core expression or scope require discussion only for affected objects, never a whole-work rollback. Unrelated feedback/registration does not invalidate the recorded agreement. Query, summarize or temporarily export history only when useful to the user; exports never become the authoritative plan.

Read supplied scripts and inspect the actual rough cut. Preserve intent when normalizing outdated timing or example materials. For substantial visual routing, use `references/visual-grammar.md` as an optional reasoning aid, not a required checklist. A cue-specific style has priority within its stated scope; source timing, output safety and implementation limits still apply.

Ask one focused question only when multiple reasonable interpretations would materially change the commissioned object, scope, continuity, or authorization. Decide implementation methods and reversible local creative choices yourself; do not ask again when the user already made the objective clear. Apply this equally to first design and later Review/chat feedback. Do not make the user choose static/motion categories or perform a stage rollback. Continue unaffected work while a necessary clarification is pending.

When a cue recomposes multiple excerpts, require the user's actual selection/order or exact authorized extraction ranges. A rough cut alone does not authorize invented editorial choices. Reuse coherent supplied materials without forcing them to match illustrative filenames. Additional audio production, source recutting and Handles/sourceIn placement remain out of scope.

Motion defaults: readable travel, perceptible easing, useful holding time and editing room, chosen for the cue rather than a universal duration. Purposeful drift or continuous motion is allowed when meaningful. Align the intended visual state to semantic narration anchors; retain rational FCPXML frame time. Never slow original footage without authorization.

## First design and the active creative loop

For fresh work model 2.2, every animated Cue needs a real concept image before code production, including simple text and annotations. Follow: understand and discuss the content → close the proposed list with the user → develop and refine concept images → user confirms the visual direction → author code → inspect real Storyboard frames and motion. Default to the image-generation tool available in Codex, without fixing a model or silently using a paid API. External model images have equal standing and do not need regeneration. Design with the script, narrative stance, relevant original frames, aspect ratio and key text; propose metaphors, wording and expression when useful. Aim for clear, coherent, natural results. The first Storyboard, motion implementation and later revisions all use the confirmed concept as their visual basis. Preserve its composition, visual style, hierarchy and material relationships except for changes the user explicitly requests. Choose implementation methods yourself; not imitating every generated pixel allows reasonable implementation differences, not replacing the adopted typography, materials or layout with an easier design. Compare actual corresponding key states with the confirmed image.

For concept-image prompting, revision and comparison, use the method in [visual grammar, section 4](references/visual-grammar.md). Carry the creative task into a concise natural-language brief: what the audience should understand, what the footage and added design each contribute, the exact content, how elements appear over time, and the single moment this image represents. Identify each reference's role (source composition, spatial relationships, visual style or edit target). Separate actual constraints and explicit taste choices from open design decisions. Let the image model explore typography, hierarchy and composition within that context; add specific visual direction when the user, adopted defaults or observed results justify it. Prompt length and exhaustive styling parameters are not quality criteria.

Own the image iteration: inspect the result, retain what works, and make targeted corrections without handing every attempt back to the user or asking permission for routine regeneration. When the overall direction is wrong, return to the original materials and current brief rather than repeatedly editing the rejected style. Check both a coherent still and plausible staged composition: independent elements, intermediate states, source visibility and reading/subtitle space where relevant. Animatability concerns layers and temporal relationships, not reducing every idea to familiar code primitives; actual motion is checked after concept confirmation.

When comparing directions, hold the content, source moment and use requirements comparable. Each candidate must solve the task with a meaningful difference in expression or visual organization; palette swaps and unsuitable filler do not satisfy a request for distinct directions. The user judges aesthetic fit and adoption. Retain reusable method, not a universal taste rule derived from one accepted or rejected image.

Bound autonomous image exploration per stable creative object and exploration round: at most **3 style directions**, stop after **3 consecutive unsuccessful corrections of the same problem**, and at most **9 actual image-tool calls**, including failures and actual retries. Same-style corrections do not create new directions. These are stopping limits, not targets: stop when satisfied, or earlier when results loop or clearly do not improve. Before each call read the current record and use `creative-planning/begin-image`; after the call register every candidate with its returned `planningAttemptId`, inspect images, and use `finish-image` with the actual tool reference and judgment. One call returning several images counts once; a call covering several objects counts once for each. Repeating the same write request does not add a call; actually calling again does. User-supplied images do not consume this budget.

An interrupted pending call occupies one slot and remains unknown until reconciled with actual tool evidence; do not reset it as uncalled or blindly regenerate. Technical Cue renaming, session changes and retries do not reset the object round. Autonomous rounds are separate from `concept.round`. At any limit, submit existing candidates, the recommendation and unresolved problems through formal Review and wait. An explicit user request to continue can open `creative-planning/continue` with the real source, retaining old rounds. Already-produced images must still be archived even after a limit; stale results must not replace a current recommendation automatically. The Agent judges style and problem resolution by looking at images. This record does not intercept arbitrary image tools or affect render identities, concept confirmation, Storyboard approval, production qualification or delivery. Exact requests and recovery details are in [operation details](references/agent-operations.md).

Before confirmation, generate, revise, compare and recommend images autonomously. Recommendation and a bare upload are not confirmation. After each image-tool generation or import, promptly copy every candidate to this version's `.staging/creative-inputs/<round>/` and register candidates together through `update operation: "concept", action: "register-batch", items: [...]` (single `register` remains compatible); owned image bytes, source provenance, short idea/motion notes and the Cue/object association persist independently of chat links. Use `origin.kind: "codex-generated"|"user-imported"`, an actual source `reference`, and a model only if known. Each batch item explicitly supplies `recommend`; at most one per object may be true, and all false is valid. Batch registration never adopts or confirms. Use `recommend: false` for intermediate or rejected candidates; all candidate images belong in `assets/concepts/`, independent of whether they are recommended or confirmed. Publish references, source frames and prompt/source records through `update` to `assets/design-inputs/` before using them, and reference the readable version-owned copies. Keep the original tool path or call reference for provenance, but do not rely on `.codex/generated_images`, chat links or temporary absolute paths as the only usable copy. Use `assets/materials/` for actual production materials; existing previews/cache/jobs/releases retain their writer-owned roles. The “画面方案” page shows these images, not rendered production frames. Images are not Storyboard or Demo artifacts. If generation is unavailable, use an external image without claiming the Codex generation path was tested.

The page action “采用这版候选” selects a recommendation only. Use `concept/propose` for an unconfirmed candidate in the current round, or `concept/select` with `conceptId` and the user's actual `source` when selection needs a revision or historical reuse. Selecting a different image after confirmation explicitly opens a new round atomically, records the reused image with `copiedFromConceptId`, and waits for confirmation; selecting the already confirmed image does not reopen. Preserve original records and feedback across the source chain. Record explicit concept confirmation using `decision kind: "confirm-concept", conceptIds: [...]` and the user's real `source`. One clear natural-language instruction can confirm several images; no duplicate page click is needed. Providing a picture and explicitly confirming its visual direction can be one `register` request with `adopt: true` and `source`; never wire a mere candidate-selection button to this combined confirmation. For an already confirmed design, start a new concept round only when the user explicitly requests concept-image changes: `operation: "concept", action: "reopen", cueIds, source`. Ordinary production feedback, implementation changes and technical renaming retain confirmation. Candidate image history and its comments remain attached to their original images. Retain concise iteration notes for non-recommended history candidates so users can revisit intermediate designs without replacing a confirmed image. Missing confirmed image bytes require recovery of the owned image, not erasure of its historical confirmation. See the exact interface in `references/hyperframes-single-source.md`.

The concept-page top action “确认方案，继续制作分镜” uses `update operation: "concept-handoff"` with selected `cueIds`, aligned exact `conceptIds`, `excludedCueIds`, a stable `requestId`, latest `expectedRevision` and actual user `source`. Pending selected concepts and the selected/excluded object scope persist atomically as `storyboardHandoffs`, even when every selected image was already confirmed. On continuation, read `summary.conceptHandoff` (or full `status.conceptDesign.storyboardHandoff`) and respect the saved scope; `current`/`problems` only advise whether its selected basis still matches. This records the storyboard handoff, not a new production gate or Motion, Demo or delivery authorization. The browser does not wake an Agent or start rendering; return to the conversation to continue. Ordinary concept confirmation from chat remains sufficient, without a duplicate page action. A saved write followed by failed refresh retains its actual receipt; retry the read rather than create a new write.

Keep one big Cue when it expresses a continuous animation. Use `finalAnimationDescription` for its overall intent, optional `cue.storyboard.frames[].narration` for the original sentence shown with each specific frame (prefix real dialogue with `原声：`; frames may repeat a sentence), and optional `cue.storyboard.animationNotes: [{id, frameIds, text}]` for local narration triggers, state changes and final holds. A frame without `narration` must be shown as `尚未标注对应旁白`; do not infer it from time, Cue-level narration or notes. Notes may share frames; some frames need none. Maintain stable IDs and valid references in the same edit when regrouping. Notes have no independent approval or lock. Text-only edits require a new Storyboard snapshot through the normal preview entry point, which reuses verified PNGs without rendering; neither the old snapshot nor its comments silently becomes evidence for the new text. The Review uses a continuous vertical scene list, with each scene’s image/video on the left and text/feedback on the right. Storyboard and the scene’s animation switch within one card; frame selection is compact. Storyboard checks the actual implementation after concept confirmation; it does not require a second first-design approval. Its “确认此场” records `scene-review` progress against the actual Storyboard or animation identity, without authorizing production or becoming a new gate for ordinary edits. Current unresolved feedback still needs attention even when historical confirmation exists. Existing concept qualification survives ordinary production revisions. The top “确认本轮，生成整片 Demo” action separately commissions production. When the user hands off production from Storyboard, read `summary.productionRequest` (or full `status.storyboard.productionRequest`): a pending record is an explicit `authorize-demo` commission with optional reviewed `storyboardIds` (or `reviewArtifactId`/`reviewRoundId` for a Demo rework), selected `cueIds`/`presentationCueIds`, exclusions and a `taskId`. Code-based exploration also requires concept confirmation in work model 2.2; image candidates, material registration and text planning remain available before confirmation. Historical 2.1 versions retain their original Storyboard and bounded `explore-motion` semantics. Do not use that historical exception to bypass the new concept-first path.

After first confirmation, the creative object remains active for the user's requested font, composition, placement, motion changes or complete redesign. Active means continuing authorized work, not independent permission to redesign the confirmed image. Execute explicit requested changes directly, including local tests; do not require a stage rollback, another first confirmation, or completion of a page feedback round. Whether the resulting media/review is still valid is a separate question. Technical deletion, rebuilding, renaming or changing files does not decide whether it is the same creative object. Declare a known relationship; ask one focused question only when reasonable interpretations change the commissioned object, scope, continuity or authorization. Across versions, use the user's explicit commission rather than inferring inheritance.

Full Demo creation requires explicit current task intent as well as first eligibility for every animated layer being produced/presented. A clear “改完给整版” can establish that intent once together with the changes. Do not ask again for the same task or require a duplicate UI click. ## Author once and preview

Canonical layout, text, styles and materials live in `compositions/cues/<cue>.html`; motion lives in `compositions/motion/<cue>.js`. The composition links its motion file. Static layout must be declarative: executable scripts and time-driven behavior belong to Motion and are rejected from Storyboard output. The static profile permits one-frame raster images, local SVG and fonts; animated GIF/APNG/WebP require Motion. Unsupported source capabilities fail closed. `srcset`、`image-set` and SVG resource references join the registered local closure. Rendering uses an isolated closure and restrictive CSP; this boundary does not claim to prove arbitrary JavaScript safe. Declare dependencies in `renderAdapters.hyperframes.layoutDependencies`; remote or missing assets block rendering. Publishing Motion checks the complete declared source dependency closure, not merely whether a `motionSrc` keyword appears. Copy only referenced fonts/materials. Keep needed sources local and reproducible.

Decide the output role from the confirmed design, motion description and relationship to the footage, including changes within one Cue. Where the original footage should keep playing, render only the added elements and leave their surrounding area transparent; an intentional magnification window may contain source pixels. Render full coverage where the design calls for a complete image or fusion. Keep footage used only as an alignment/reference background in the review composite, out of the animation layer. Choose representative times and native-coordinate Alpha checks yourself, including intended transparent entry/exit states; never change declarations merely to accommodate a wrong render or ask the user to fill coordinates. Inspect both the independent asset and the composite. An Alpha channel and correct transparency are different facts; the sampled check semantics are in [the media contract](references/hyperframes-single-source.md#alpha-与交付).

For an ordinary local Cue edit, prefer `cueUpdates: [{cueId, changes}]` inside `operation: "edit"`: omitted fields remain, dictionaries merge and arrays replace; it cannot rename/delete Cues or rebind objects. Use whole `patch.cues` only when the authorized operation actually needs the complete list. Keep CSS/JS publication in the existing `files` entry; the full affected dependency closure is still checked. See [request examples](references/agent-operations.md).

Prepare files under the version's `.staging/`, then publish them with one `update` request (`operation: "edit"`, `files: [{path, source}]`, and optional `patch: {brief, cues, project}`). Do not hand-edit live manifests, evidence, jobs or releases. Descriptive changes do not alter media identities; source, duration, screen text or font changes do. Placement-only changes reuse animation MOV and rebuild composition. Existing real samples continue into production rather than being recreated in a second storyboard.

python3 <skill>/scripts/serve_workflow_review.py "/workspace/AfterForge"

Every writing request uses a unique `requestId` and the latest version `expectedRevision`. Retry the identical request to deduplicate. Freeze a comment’s version, object, frame/artifact and playback-time anchor when input begins; navigation must not silently retarget a draft. On conflict retain the proposal/comment and original location; reread and reconcile rather than silently retargeting.

HyperFrames renders 480p cue media; FFmpeg composites all overlapping cues with original local times, layer order, rough-cut picture and sound. A complete full-length sample plus full-duration supplements for overlapping cues form the formal review set. When the user explicitly states that all current individual animations have been reviewed and requests delivery without a full Demo, use update `operation: "collect-review"` with explicit `artifactIds` and the actual user `source`. This creates an `individual-cues` review set only if one current eligible isolated movie covers the entire duration of every animated Cue. It does not generate or claim a full-timeline review, and does not itself approve or authorize delivery. Scene-review progress alone is insufficient. Do not infer that the user watched everything.

## Feedback and decisions

Autonomous media playback/navigation requires a fixed sample or a supported seekable implementation; production authority alone does not make autoplay deterministic. Fixed backgrounds record source SHA and sampling time. Explicit no-narration facts may satisfy narration context without inventing placeholder copy.

Use the same `update` API for chat and page feedback. Preserve original text and `source: {channel: "chat"|"review", text, reference}`. Targets may include version, artifact, segment IDs, multiple cues, or a global interval; do not preselect one overlapping cue. The shared target resolver is used for first confirmation, approval and delivery. Record clarification and resolution on feedback; `addressed` means the Agent changed it, `accepted` requires a user decision. Keep the resolved animation description concise and separate from discussion history. Concept confirmation requires the current recommended image with its registered nonblank `idea` and `motion` notes, complete two-channel `contentContext`, and no applicable unresolved feedback: `present` reads real canonical text, `none` has an evidenced basis, and `unknown` blocks confirmation. `finalAnimationDescription` describes the production/Storyboard intent; it is not a concept-confirmation requirement. With a user `source`, `feedbackResolutions: [{feedbackId, action: "accept"|"defer"|"withdraw"}]` may resolve applicable feedback atomically with confirmation.

Approval and authorization bind the current verified complete review set. `operation: "decision", kind: "approve"` records picture approval only; `authorize` requires that set already approved. A clear instruction to approve and produce this delivery is supplied as `decision: {kind: "approve-and-deliver", reviewSetId, source}` to `deliver`. Never infer authorization from freezing, successful rendering, historical approval, or a positive reaction to an image.

```bash
python3 <skill>/scripts/afterforge.py deliver "<version-root>" --request-file /tmp/deliver.json
python3 <skill>/scripts/afterforge.py resume "<version-root>" --request-file /tmp/resume.json
```

Resume uses `jobId` and current `expectedRevision`. Jobs retain verified cue results after failure. Changed inputs require a new request and reuse unaffected media. Final delivery covers every animated cue, verifying native 1920×1080 ProRes 4444, exact source frame rate/duration, decoded alpha, source timeline invariance, placement, references, DTD and package inventory. No-animation episodes return “无需动画交付”.
