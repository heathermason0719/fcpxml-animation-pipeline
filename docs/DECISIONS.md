# 重要决策

## 采用“Codex Skill + 确定性脚本”的项目形态

**决定：** 使用 Codex Skill 组织创作判断、工作流程和工具调用；将 FCPXML 解析、时间计算、素材注册、格式转换与回填等易出错操作放入可测试的确定性脚本。

**原因：** 动画细化需要理解语义和上下文，而时间线回写要求稳定、可重复和可验证。把两者分开可以降低 XML 损坏和时间漂移风险，也便于跨项目复用。

**主要替代方案：** 将全部逻辑写进单次提示词，或只制作一个独立命令行程序。前者难以保证机械操作一致性；后者不适合承担需要内容理解的动画设计判断。

**影响：** 后续目录和接口需要清楚区分 Skill 指令、确定性脚本、参考资料、模板资源和项目输入输出。

## 将动画清单作为渲染与时间线之间的稳定契约

**决定：** 旁白、字幕、粗略动画要求经过分析后，先形成结构化动画清单，再由渲染后端消费；FCPXML 回填也以该清单和实际渲染结果为依据。

**原因：** 统一中间格式可以让动画设计接受人工审阅，并避免整个流程绑定到单一渲染工具。

**主要替代方案：** 分析阶段直接生成 HyperFrames 工程并从工程反推回填信息。该方案耦合较高，更换渲染器或重新审阅动画设计时成本较大。

**影响：** 后续必须定义并验证动画清单的数据模式，HyperFrames 只是首个适配器。

## 使用非破坏性的 FCPXML 回填方式

**决定：** 始终保留用户原始 FCPXML、FCPXMLD 和媒体，生成新命名的时间线交付物，不直接修改 Final Cut Pro 资源库。

**原因：** 时间线和媒体属于高价值创作资产，自动化流程必须可回退，并允许用户在导入后对比检查。

**主要替代方案：** 原地修改 XML 或直接操作资源库。两者都增加数据损坏、引用失效和难以恢复的风险。

**影响：** 所有脚本和验收流程必须把输入视为只读，并验证输出素材引用的完整性。

## 用单一交付协议版本约束可复用 FCPXML 包

**决定：** `deliveryFingerprint` 除业务输入外，必须包含由 FCPXML 交付后端持有的稳定常量 `deliveryProtocolVersion`。它是既有交付设计中“回填策略版本”的规范名称和唯一实现，不再建立并行的策略版本、包格式版本或生成器版本。

**原因：** 即使原 FCPXML、动画资产和回填位置完全相同，FCPXML 注入、时间映射、lane 分配、媒体引用、Event / Project 身份处理或包结构的语义修复也可能改变最终交付。若指纹只覆盖业务输入，更新后的生成器可能错误复用旧包；显式语义版本可以让后端在这类变化发生时确定性地产生新指纹。

**主要替代方案：** 使用 Git commit、实现文件哈希或每次都生成随机新包。前两者会把不改变输出的重构误判为协议变化，也可能遗漏环境外语义；后者失去相同输入的验证复用能力。

**影响：** 会使相同业务输入产生语义不同交付结果的后端改动必须提升 `deliveryProtocolVersion`；不改变输出语义的重构不提升。该版本只属于交付后端和交付指纹，不进入 manifest 业务权威、不参与 A11 冻结，也不改变非破坏性回填目标。

## 用 manifest 注册稳定交付资产，render ledger 只保留执行证据

**决定：** 每条 `animated` cue 在正式 MOV 重新探测并验证后，把后端无关的 `deliveryAsset` 注册进主 `animation-manifest.json`；`source-only` cue 不注册。`render-ledger.json` 只证明一轮渲染如何执行，不成为 FCPXML 生成器的长期依赖，也不创建第二份 delivery manifest。

**原因：** manifest 已经是分析、渲染与回填的稳定契约。让 FCPXML 直接依赖 HyperFrames ledger 会把交付后端绑定到特定渲染器；另建 delivery manifest 则会重复保存 cue、媒体和时间状态并产生漂移。

**主要替代方案：** 直接消费 render ledger，或新增独立 delivery manifest。两者分别造成渲染器耦合和双重权威。

**影响：** 注册器必须重新读取实际 MOV，把稳定文件名、哈希、规格、时长和 alpha 状态写入 manifest；manifest 不保存正式包绝对路径。`deliveryAsset` 不改变 A11 已批准布局的冻结边界。

## 使用 AfterForge 根层的扁平、不可覆盖 FCPXMLD 交付包

**决定：** 正式 `.fcpxmld` 直接发布在项目级 `AfterForge/` 根层，包根目录只平铺一个 `Info.fcpxml` 和已注册动画 MOV。XML 使用同级相对路径；同卷优先 hard link，失败时复制。包名包含 `deliveryFingerprint`，已有正式包不得原地覆盖。

**原因：** 深层媒体路径在实际 Final Cut Pro 工作流中可能改变资源库外媒体引用和代理/优化媒体行为。扁平、自包含且不可覆盖的包便于移动、验证、回退和问题定位。

**主要替代方案：** 在 Vn 深层 `delivery/Media/` 发布、写入构建机绝对路径，或覆盖固定名称包。它们分别增加 FCP 媒体管理风险、破坏迁移性和丢失历史结果。

**影响：** 包内不包含 manifest、ledger、日志、临时文件或原电影媒体。包构建必须在同文件系统临时目录完成全部验证后原子发布；相同 fingerprint 只允许验证复用，损坏包必须阻塞而不是自动覆盖。

## 创建新 Event / Project，并以独立 connected clips 粗略回填动画

**决定：** 输出创建新的 AfterForge Event 和 Project，Project 是原目标 Project 的完整时间线副本，只增加每条 `animated` cue 对应的独立 connected clip。第 6、7 镜等 `source-only` cue 不生成占位；动画使用实际 MOV 时长，按目标镜头或语义段落粗略定位，不追求帧级旁白同步。

**原因：** Final Cut Pro XML 导入没有可靠的“直接追加到既有 Event”交付路径，用户也需要把每条动画继续移动、裁切、禁用或复制。完整复制并叠加可以保持非破坏性，同时给粗剪阶段保留微调空间。

**主要替代方案：** 更新原 Event / Project、统一 secondary storyline、compound clip、完整透明覆盖层或逐帧旁白同步。这些方案会增加原项目风险、降低逐条可编辑性，或把不必要的精度成本转嫁给粗剪。

**影响：** 输出不得沿用可能触发既有对象更新的 Event / Project 身份；除新身份、动画资源和 connected clips 外，必须证明原 sequence 语义不变。lane 根据时间重叠确定，时间映射使用源 FCPXML 有理数并支持嵌套、`offset`、`start` 和 `timeMap`。

## 以自动验证、首次实际导入和协议级 round-trip 建立交付基线

**决定：** 正式包只有在媒体、DTD、引用图、时间位置、原时间线不变性、包结构和幂等性验证全部通过后才发布。首个真实 V1 必须完成 Final Cut Pro 实际导入和再导出 round-trip；后续仅在 FCPXML 或交付协议语义变化时重复 round-trip。

**原因：** DTD 只能证明 XML 结构合法，不能证明 FCP 一定正常导入、保持相对媒体引用或按预期规范化时间线。另一方面，每个普通 Vn 重复完整 round-trip 会制造没有必要的人工成本。

**主要替代方案：** 只做 DTD / 脚本验证，或每版都做完整 round-trip。前者覆盖不足，后者不符合高频生产效率目标。

**影响：** `2026-08-26_V1` 是首个端到端基线；后端实施完成前不能宣称 FCPXML 交付能力已经成立。机器验证工程正确性，不重新评价动画审美或要求逐帧同步。

## 采用“工作区优先、阻塞才询问”的项目入口

**决定：** Skill 先接收用户的实际项目工作区并自动发现已有材料。只有 FCPXML/FCPXMLD、低码粗剪参考视频缺失或无法唯一确定，或者时间线无法解析时，入口才向用户提出最小必要问题。animation brief、逐镜设计稿、品牌资料和重复旁白格式不作为默认必填项。

**原因：** 用户的真实剪辑习惯是在 Final Cut Pro 粗剪中保留动画空缺，并把字幕、Marker、时间线文字或 notes 留在现有项目材料里。重新要求逐项搬运或补写设计输入既重复劳动，也会削弱 Skill 对实际项目上下文的利用。

**主要替代方案：** 使用固定上传清单，要求 FCPXML、参考视频、SRT、动画 brief 和视觉规范全部齐备后才开始。该方案容易产生多余询问，并把本应由 Skill 承担的动画设计转嫁给用户。

**影响：** 入口必须输出可验证的材料选择、证据、warning、ambiguity 和 blocker；普通歧义先保留，只有具体条目真正阻塞后续可靠判断时才请求用户确认。

## 分离用户侧工作目录显示名与 Skill 内部身份

**决定：** 在每个真实项目根目录建立独立用户工作目录，当前默认显示名为 `AfterForge`。该名称只承担用户可见门牌号职责；仓库名、Skill ID、协议、字段和内部索引继续使用 `fcpxml-animation-pipeline`。显示名由初始化器参数提供，可独立更换。

**原因：** 用户需要在项目目录中直观看到 Skill 的工作区域，但用户侧品牌名称可能变化。把显示名写入内部身份会导致无关迁移，并破坏已有测试和协议稳定性。

**主要替代方案：** 将 Skill、仓库和数据模型整体重命名为 `AfterForge`。该方案把可变展示名称错误提升为核心身份，迁移成本和兼容风险都没有必要。

**影响：** 初始化器必须幂等创建或识别工作目录，保留已有内容；其他组件不得因为默认目录名变化而修改内部标识。

## 分离用户投料区与 Skill 产物区

**决定：** 项目根目录使用两个职责互斥的顶层目录：`user-inbox/` 由用户维护、Skill 全程只读；`AfterForge/` 由 Skill 维护，并继续作为唯一默认写入区。用户在 `user-inbox/` 下自行创建和选择 `YYYY-MM-DD_Vn/`，版本材料平铺在该目录根层。

**原因：** 用户需要按轮次投放真实输入，同时必须防止 Skill 把分析产物混入用户材料或改写历史版本。输入与产物物理分离后，读写权限可以被明确验证。

**主要替代方案：** 让 Skill 自动创建 V1、选择最新版本或在同一目录混放输入和输出。这会引入未经授权的版本管理，并增加误改用户材料的风险。

**影响：** 初始化器只负责 `user-inbox/` 顶层目录；所有版本管理由用户承担。intake 读取用户明确指定的版本目录，任何默认产物写入都必须位于 `AfterForge/`。

## 分离用户语义锚点与机器精确时间

**决定：** FCPXML/FCPXMLD 是时间位置、项目帧率和有理数时间基准的唯一权威。用户动画脚本不再要求填写帧级精确开始与结束时间，而是使用对应旁白原句及可选的开始、结束触发词句定位；开始或结束触发留空时，默认使用整段对应旁白的范围。系统在分析阶段把这些语义锚点解析为机器可验证的精确时间，回填时仍按源 FCPXML 时间基准写入。

**原因：** 透明动画回到 Final Cut Pro 后仍需由剪辑者微调。让用户为了可调整素材额外维护帧级时码会增加无效劳动，也容易与后续粗剪变化产生冲突；语义锚点更符合实际剪辑表达，同时不削弱机器回填的精确性。

**旁白证据权威：** 参考视频中的实际口播负责“真正说了什么”；脚本、SRT、时间线字幕和转写稿负责检索、分段与对齐，允许包含未经人工校对的错别字。明显笔误可依据实际口播自动校正；只有差异影响语义或无法可靠匹配时才进入人工确认。

**主要替代方案：** 要求用户逐条填写精确时码，或直接把 SRT 时间当作回填权威。前者增加剪辑内耗，后者会把自动转写误差和版本漂移带入 XML 回填。

**影响：** `animation-manifest.json` 必须同时保留用户原始语义锚点和系统解析后的精确有理数时间；不得把未经校验的脚本时码、SRT 时码或浮点秒数直接写回 FCPXML。动画成片可以保留便于剪辑的时长余量，不要求用户提供帧级精确出点。

## 采用 480p 审阅与 1080p 最终动画的双层渲染规格

**决定：** 16:9 横屏自媒体 V1 在最终渲染前使用 854×480 的轻量审阅预览；预览把动画叠加在对应粗剪画面上，并保留参考视频自带的口播原声，只承担动画效果确认职责。用户确认后，最终透明动画统一渲染为 1920×1080 ProRes 4444 MOV，帧率跟随源 FCPXML；当前真实项目为 24 fps。源时间线即使因电影素材采用 4K，也不要求动画制作 4K 版本。

**原因：** 480p 足以反复检查构图、节奏和叙事效果，能够显著降低迭代渲染负载；最终 1080p 可以保持协议界面、角色卡、字幕和细线条的清晰度，并与计划上传的 1080p 成片匹配。720p 作为统一最终动画规格仍需放大到 1080p，对文字和透明边缘的节省得不偿失。

**主要替代方案：** 全程 4K、全程 1080p，或最终统一 720p。前两者提高迭代成本，后者降低文字与图形边缘质量。

**影响：** 渲染适配层必须让布局和动画在 480p 审阅与 1080p 最终输出之间保持一致；480p 合成预览不得被误当作 Final Cut Pro 回填素材，最终回填只引用 1080p 透明动画。

## AfterForge 不承担声音制作

**决定：** AfterForge 不生成、设计、混合、交付或回填音效与音乐。`animation-manifest.json`、storyboard、HyperFrames Vn 工程和最终 FCPXML 均不建立声音制作字段或素材引用。480p 审阅视频只保留粗剪参考视频自带的原声，用于理解旁白和判断动画节奏。

**原因：** 两轮真实试制中的生成声音整体方向均不符合用户需求，继续校准会把工作流精力投入非核心能力。动画视觉与时间线回填已经可以独立成立，声音由用户在剪辑台另行处理更直接。

**主要替代方案：** 继续生成逐条 WAV，或只在 480p 审阅中制作临时混音。两者仍需要额外设计、生成和验收，且不能证明能提高动画工作流的整体命中率。

**影响：** 工作流删除声音方向设计、音频生成、音频验收和音频回填步骤；粗剪原声仍可作为旁白内容与节奏证据，但不属于 AfterForge 产物。

## 为每个视频冻结整体视觉包装与统一运动气质

**决定：** 每个视频项目在正式动画实施前单独确认并冻结两类创意方向。第一类是项目级 canonical `AfterForge/frame.md`，负责整体视觉包装审美，包括艺术方向、构图原则、信息层级、图形语言、背景与前景、形状与组件、材质与纹理、影像处理、色彩、字体、间距和视觉禁区，而不只是颜色与字体。创建 Vn 时复制当时的 canonical 文件为本版构建快照，并在 manifest 中记录路径与 SHA-256。第二类是视频级统一运动气质，记录在 `animation-manifest.json` 的 `creativeDirection.motionDirection` 中，包括运动性格、节奏、速度与重量感、缓动倾向、入退场逻辑、转场原则、停顿方式和动效禁区。

**原因：** 同一套视觉模板不适合无条件复用到所有视频；颜色和字体一致也不足以形成统一包装。与此同时，逐条独立决定运动方式容易让同一视频出现轻重、速度、缓动和转场语言互相冲突。把视觉包装和运动气质都提升为视频级先决条件，可以让后续每条动画在允许内容变化的同时保持同一作品的整体感。

**主要替代方案：** 只选择 HyperFrames 风格预设，或让每条动画各自决定视觉和运动。前者会把视觉规范缩减为预设皮肤，后者容易形成片段之间彼此割裂的动效拼盘。

**影响：** 风格选择发生在逐条动画方案设计之前。HyperFrames 使用当前 Vn 内的 `frame.md` 快照和具体动画规则；canonical 后续变化不得静默改变旧版。其他渲染后端也必须消费 manifest 中的运动气质、视觉方向摘要和本版视觉快照，不得依赖 HyperFrames 私有工程反推创意决定。

## 在具体设计前增加视觉语法路由

**决定：** 每条候选动画在形成具体方案前，按“信息功能 → 与原画的关系 → 可参考的视觉语言”完成设计路由。功能和参考语言使用开放索引；每条动画确定一个主功能和一个主原画关系，允许记录次要功能及辅助关系，但必须保持从属并说明理由。A、B 两种原画关系可以混合，仍必须冻结主关系。“照顾、避让、保留原画可见性”本身不构成 B；只有原画承担不可替代的信息或叙事功能时才计入 B。混合态通过分别删除包装和原画的双删除测试确认，只有两层各自均承担不可替代功能时才成立。路由结果写入 `animation-manifest.json` 的 cue 级 `designRoute`，并以稳定 cue ID 和已有原镜号在既有 A11 storyboard 联合验收中暴露。

**原因：** 直接从旁白或粗略要求跳到卡片、HUD、配色和特效，会让熟悉的表现形式替代真正的信息任务，也难以区分方向判断错误与具体执行问题。先固定功能及包装与原画的关系，再选择参考语言，可以给未来 Agent 稳定的判断依据，同时通过开放索引保留具体设计自主空间。

**主要替代方案：** 把视觉语法写进每个项目的 `frame.md`，为每条动画新增用户确认，或将视觉语言做成封闭模板枚举。第一种混淆跨项目方法与项目审美资产，第二种增加不必要的用户往返，第三种会诱导错误归类并压缩设计空间。

**影响：** `references/visual-grammar.md` 承担跨项目判断规则，`frame.md` 仍只保存本视频确认后的整体视觉包装。Agent 默认自主路由；只有分叉会显著改变任务范围、违反已确认约束或产生难以逆转的后果时才额外请求确认。Storyboard 继续是 manifest 的审阅视图，不成为第二权威源。

## 在 A7 审核可选动画脚本的可执行性

**决定：** intake 继续只发现并保留用户主动提供的动画脚本或逐镜要求，不判断内容质量，也不把脚本列为必要输入。存在 `materials.animation_guidance` 时，Agent 在 A7 对照参考视频实际口播与原画、FCPXML 时间线、AfterForge 范围和当前制作后端逐条审核，并在现有草稿 manifest 的 cue 级 `guidanceReview` 中记录 `ready`、`agent-normalized`、`needs-material`、`needs-clarification`、`out-of-scope` 或 `unaligned` 及简短依据。没有脚本时字段缺省，由 Agent 自主形成候选动画。

**原因：** 文件名识别只能证明脚本存在，不能证明其语义能对齐旁白、要求处于产品范围内或当前后端具备实现条件。若直到具体设计或动画实施后才发现这些问题，会造成方向返工；若把内容审核塞进入口，又会把可选创作材料错误升级为 intake blocker。A7 位于视觉方向和具体设计之前，既能尽早发现真实约束，也保持入口契约稳定。

**主要替代方案：** 在 intake 阶段审核脚本、为脚本单独增加一次用户验收，或推迟到 A11 才暴露。第一种混淆机械发现与语义判断，第二种增加不必要往返，第三种把素材缺失、范围冲突和对齐失败推迟到已经投入设计之后。

**影响：** 审核不创建平行报告或第二权威，不改变 intake 的 `ready` / `blocked`，也不进入 A11 layout lock。Skill 在 `assets/animation-script-template.docx` 保存一份可按需提供的八列回填模板，但不自动复制到项目或 `user-inbox/`，不拒绝自由格式脚本，也不要求用户必须填写。可直接使用和可自主规范化的 cue 不询问用户；需要素材时先记录精确需求，待 Vn 建立且该 cue 进入具体设计后再索取并保存到 Vn；只有问题会改变 A8 方向、违反范围或阻止受影响 cue 可靠继续时才单独询问。其余结果随现有 A11 storyboard 一并暴露。

## 多原片重编 cue 默认要求独立带余量片段

**决定：** 当一条动画需要在生成画面内重放、重排、裁切、遮罩、平铺或以其他方式重新合成两段或以上原片时，A7 默认将该 cue 标记为 `needs-material`，要求用户按预期进入顺序提供每个语义片段的独立、带充足余量文件。只有用户明确给出精确源范围并授权代为提取时，才允许从既有原片生成这些片段。用户最新明确说明，以及实际投放文件的名称、编号顺序和可检查画面，是素材身份与选择的权威；脚本中列出的素材类型默认只作规划参考，除非用户明确重申为硬要求。

**原因：** 粗剪参考视频和 FCPXML 源引用能证明哪些候选画面存在，但无法证明用户希望使用的精确动作、余量与重编顺序。这些都是导演/剪辑选择，不是 Agent 可从可用性自行推断的技术事实。

**主要替代方案：** Agent 默认从粗剪或 FCPXML 反推取段，或对所有包含原片的 cue 都要求用户重复导出。前者会将创作选择伪装成技术规范化，后者会对只需顺着当前原画做遮罩或叠加的简单镜头增加无效负担。

**影响：** 该规则是 cue 级门槛，不把独立原片升级为整个 invocation 的 intake 必填项。标准可接受输入为 1920×1080 H.264、匹配 FCPXML 的恒定帧率、Rec.709 SDR，前后各至少约 0.5 秒可用余量，不预烘焙裁切、调速、边框或动画，音频可省略。文件名使用 `01-` 等顺序前缀，或保留 `animation-source`、“动画素材”等明确信号时，intake 将其记入 `materials.animation_source_clips` 而不与低码粗剪参考视频竞争；带顺序前缀但包含粗剪关键词的文件仍保留参考候选身份。实际素材与用户说明一致但与脚本素材举例不同时，A7 记录 `agent-normalized` 并继续；只有用户说明、文件名、编号顺序或可检查画面相互冲突时才询问。ProRes 或 4K 只在大幅放大裁切、抠像、重度影像处理或近全画幅重用时按需要求；最终交付仍为 1920×1080 透明 ProRes 4444。

## 逐镜明确风格要求优先于项目默认风格

**决定：** 项目级 `frame.md` 与视频级统一运动气质负责未特别说明部分的默认风格。用户动画脚本若对单条镜头明确指定视觉或运动风格，该逐镜要求在对应 cue 及其明确属性范围内具有更高权威；未指定属性继续继承项目默认。A7 在 `guidanceReview.notes` 记录原始证据和覆盖范围，后续 `designRoute` 与 A11 必须呈现实际采用的风格。

**原因：** `frame.md` 的职责是保证整部视频的统一性，但逐镜脚本承载用户针对具体叙事任务的明确创作意图。用通用禁区或默认组件抹去逐镜要求，会使风格一致性反过来损害镜头表达；让逐镜要求只覆盖明确范围，则能同时保留用户意图与未指定部分的一致性。

**主要替代方案：** 让项目级 `frame.md` 无条件压过逐镜脚本，或把单条镜头要求扩大为全片风格变更。前者会忽略用户明确指令，后者会把局部例外错误传播到其他 cue。

**影响：** 逐镜风格覆盖不能改变 FCPXML 时间权威、AfterForge 产品范围、`user-inbox/` 只读边界、交付协议或后端能力限制。覆盖对象或范围不清时必须在 A7 标记 `needs-clarification` 并询问，不能由 Agent 猜测或扩大解释。

## 将 Storyboard 作为合并验收视图而非第二权威源

**决定：** 保留 storyboard 阶段，但 `STORYBOARD.md` 只作为 HyperFrames 适配层从草稿 `animation-manifest.json` 生成的用户审阅视图。系统内部先完成逐条文字方案，再制作使用真实文案的静态关键画面；两部分准备完成后合并为一次用户验收，不在内部步骤之间增加一次确认。用户反馈先修正草稿 manifest，再重新生成 storyboard 和受影响的关键画面；确认后 manifest 才进入 `approved` 状态。

**原因：** V2 试制证明，仅从文字要求直接进入完整动画会遗漏标题与卡片从属关系、元素数量和运动重量等可视化语义；但分别验收文字方案和线框又会增加不必要的用户往返。把真实文字、结构说明和静态关键画面放在一次验收中，可以在低成本阶段发现误读，同时保持工作流简洁。

**主要替代方案：** 把 `STORYBOARD.md` 作为独立权威源，或完全跳过 storyboard。前者会与 FCPXML 和 `animation-manifest.json` 形成重复且可能冲突的数据源；后者会把结构误读留到完整动画完成后才暴露。

**影响：** FCPXML/FCPXMLD 继续独占精确时间权威，`animation-manifest.json` 继续作为分析、渲染与回填的稳定机器契约。Storyboard frame 只表示供审阅的关键画面卡，不表示帧级时间码；HyperFrames Studio 的逐卡评论属于临时反馈通道，不直接改写 XML。

## A8、A11 只阻塞无法验收的工程故障

**决定：** A8 视觉方向验收与 A11 storyboard 联合验收以尽快把可查看结果交给用户为优先。低成本、确定性的自动检查可以保留，但只作为非阻塞自检；不再为了重复检查内容、结构、浏览器截图或视觉效果延迟交付，也不要求 Agent 代替用户完成审美验收。只有 storyboard 无法打开、关键资源缺失、页面明显报错等导致用户无法正常查看目标产物的问题才构成 blocker。检查工具自身失败但不影响用户查看时，记录限制并继续交付。

**原因：** 实际 A8、A11 迭代已经证明，内容复读、结构检查、lint 和 Agent 浏览器预览全部通过，仍不能替代用户发现真实视觉问题；这些重复检查增加了交付等待，却没有减少必要的用户验收。机器在这两个阶段最有价值的职责是挡住明确的工程故障，而不是判断“好不好看”。

**主要替代方案：** 把 lint、浏览器预览、截图比较和 Agent 视觉复核全部作为提交用户前的硬门槛。该方案会延迟高频创意迭代，并错误地把机器自检等同于用户审美确认。

**影响：** A8、A11 修改完成后，只要用户仍能正常查看结果就应尽快交付；非阻塞检查失败可以如实说明，但不得启动重复排查循环。该决定不适用于后续动画渲染、透明素材生成、FCPXML 回填和最终交付，后续阶段仍执行与工程风险相称的严格验证。

## 分离 AfterForge 项目初始化与 Vn HyperFrames 脚手架

**决定：** `AGENTS.md` 与 `CLAUDE.md` 只在创建新的 AfterForge 视频项目时于工作目录根层初始化一次。创建新 Vn 不得重新生成、复制、覆盖或自动更新这两个项目级文件。`CLAUDE.md` 创建后不进入日常同步维护；未来实际使用 Claude Code 时，再依据当时项目规则和用户授权显式更新。Vn 工程由仓库控制的确定性 `scaffold_hyperframes.py` 使用最小模板创建，不以每版执行通用 `hyperframes init` 为前提。

**原因：** HyperFrames 通用 `init` 面向独立创作工程，会附带通用 Agent 指令和环境级 skills 检查；这些行为不属于 Vn 创作内容，并可能让每个版本积累重复、过时或相互冲突的局部指令。AfterForge 同时管理一个视频项目的长期资产和多个版本，需要把一次性项目治理与可重复版本构建分开。

**主要替代方案：** 每版执行 `hyperframes init` 后删除 Agent 文件，或在每个 Vn 中保留完整副本。前者仍把两个生命周期耦合并依赖事后清理，后者会制造重复维护和规则漂移。项目级隐藏 base 模板可以作为过渡实现，但不应成为必须手工升级的第二套 canonical 工程。

**影响：** 一次性项目初始化器只负责缺失的根层项目入口，存在即保留；版本脚手架只写入全新的 Vn 目录，目标存在即阻塞，并固定 HyperFrames 版本、项目配置、frame 快照、compositions 和本地素材。HyperFrames skills 更新属于机器环境维护，不由项目或 Vn 创建隐式触发。Vn 的独立重渲染不依赖 `AGENTS.md` 或 `CLAUDE.md`。

## A11 与 A12 共享唯一正式 cue composition

**决定：** 每条 animated cue 只维护一份 `compositions/cues/<cue>.html`，其中真实文案、DOM、布局和 CSS 终态是 ground truth。运动单独位于 `compositions/motion/<cue>.js`，不得改写会触发布局分叉的尺寸、定位、字体或流式布局属性。A11 的 `compositions/review/` 和 `STORYBOARD.md` 由 manifest 自动生成，把原画 still 与该正式 cue composition 组合为 hero frame；A12 的 `index.html` 也直接装入同一 composition。`source-only` cue 不创建 composition、motion 或渲染槽。

**原因：** 旧流程分别维护静态 frame 与 animation composition，Storyboard 通过后仍可能在复制、动画化或局部修复时发生裁切和位移。事后对位检查只能发现部分漂移，不能从机制上消除两份布局实现。让 A11 直接投影正式 composition，符合 Layout Before Animation 与 CSS 终态为 ground truth，并让局部修改只作用于一个结构。

**主要替代方案：** 保留两套布局并做截图 diff，或从 storyboard frame 复制生成 animation composition。两者仍允许后续独立修改和累积漂移，长期依赖用户发现回归。

**影响：** manifest 升级为 v2，记录 `productionMode`、`workflowState`、HyperFrames adapter 路径、`heroTime`、布局依赖与 SHA-256 layout lock。A11 批准后冻结 composition、样式、字体和批准截图；依赖变化必须重新进入 A11。生成脚本拒绝覆盖手写 review。旧 Vn 可用迁移器拆出 canonical layout 与 motion，旧 `frames/animation` 在迁移对照完成前保留。

## 以 delivery-native cue 驱动 480p 审阅与 1080p 透明交付

**决定：** animated cue 的唯一正式 composition root 必须等于 manifest 的 delivery 尺寸；当前横屏项目为 1920×1080。A11 静态 hero 与 A12 完整动画继续使用 854×480，但二者都是同一正式 cue 的自动生成投影。逐 cue 透明 MOV 通过自动生成的 1920×1080 delivery host 在 composition 原生尺寸渲染，不使用 HyperFrames `--resolution`，也不允许把 480p MOV 放大后冒充正式交付。

**原因：** 原先虽然消除了 A11/A12 两份手写布局，但 canonical cue 仍固定为 854×480，导致 manifest 中的 1920×1080 只是声明而不是可执行契约。HyperFrames 0.8.16 的 alpha 渲染不能可靠用 `--resolution` 补齐该缺口；渲染后放大会保留布局但损失文字、边缘和材质的原生清晰度。

**主要替代方案：** 继续保留 854×480 canonical 并后期放大，或分别维护 480p/1080p 两套布局。前者不能提供原生 1080p，后者重新引入 Storyboard/animation 漂移和人工返工。

**影响：** validator 必须检查 canonical 尺寸与 delivery 一致；layout lock 同时覆盖 review projection 与投影规格；旧 Vn 通过确定性 legacy stage 迁移并重新接受 480p 等价审阅。新 Vn 直接按 delivery 坐标创作。只有用户通过 A12 且 lock 有效后，才允许批量渲染透明 ProRes 4444。
